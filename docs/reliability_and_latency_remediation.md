# BuildWise AI — Reliability & Latency Remediation Tracker

Status as of 2026-07-30. This document tracks the investigation into
consultations that crash mid-flow (observed at the Product Planning stage)
and the accompanying end-to-end latency. It is a living tracing doc: update
the `Status` columns and append to the Change Log as work lands — do not
rewrite history in the tables above it.

## 1. Trigger

A live consultation crashed at `product_planning` / `product_definition`
with:

```
pydantic.ValidationError: 1 validation error for ProductDefinitionDraft
features.10
  Value error, A non-excluded feature requires at least one supporting goal.
```

The task failed twice (~150s each, ~300s total) before CrewAI gave up and
the Flow raised an unhandled exception. Investigating this one crash
surfaced a set of related architectural issues that affect every planning
stage, not just Product Planning — captured below.

## 2. Current flow (for reference)

```mermaid
flowchart LR
    DISC[Discovery Crew] --> PP[Product Planning Crew\nPM to BA to Market/GTM, sequential]
    PP --> SPEC[Deterministic Specialist Planner]
    SPEC --> TECH[Technical Planning Crew\nSolution to AI to Security to QA, sequential]
    TECH --> COST[Cost Aggregator]
    COST --> LEAD[Lead Review]
```

Every crew runs `Process.sequential`; every task is one single-shot
structured-output LLM call against a large Pydantic schema.

## 5. Why compression is P0, not a nice-to-have

Two of the three highest-severity latency items (I5, I6) are, concretely,
"a stage's prompt contains the full raw JSON of every upstream artifact
instead of only the fields that stage's task actually needs." This is not
a new idea for this codebase — `planning/specialist_context.py` already
built compact, field-projected context objects and a helper
(`context_size_reduction`) specifically to measure the savings. It's just
not connected to the execution path every consultation actually takes
(same-crew `Process.sequential`). F5 is closing that gap, plus extending
the same pattern one stage earlier (Discovery → Product Definition), where
the log shows the single largest observed input payload (61,858 chars /
~15,465 tokens on one task).

Expect F5 to be the single biggest lever on latency, ahead of F6
(parallelism) — it reduces the cost of every stage's call, whereas F6 only
overlaps calls that are already individually smaller after F5.
