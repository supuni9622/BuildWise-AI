# CrewAI Runtime Latency Findings

**Analysis date:** 2026-07-27  
**Runtime inspected:** CrewAI 1.15.5  
**Documentation compared:** CrewAI 1.15.7 official documentation

## Executive summary

The observed delay is primarily caused by large structured LLM generations,
not by an infinite CrewAI loop.

In the inspected incident, Discovery made one visible OpenAI HTTP request. It
took approximately 136 seconds to return a deeply nested `DiscoveryResult`,
which then failed structured-response validation because `rag_required` was
true while `rag` was absent from the capability list.

The same exception was logged by several CrewAI layers. Those repeated error
messages did not represent repeated paid OpenAI requests in that incident.
The GET requests every four seconds were frontend status polling and did not
restart or delay the Crew.

The wider architecture can still multiply latency through:

- large Pydantic response schemas;
- large CrewAI Skill instructions;
- full upstream artifacts passed into downstream prompts;
- sequential specialist tasks;
- agent iterations;
- provider retries;
- guardrail-driven task regeneration;
- automatic context summarization;
- Lead Review receiving almost every generated artifact.

Increasing the request timeout does not address these causes. The system needs
smaller model contracts, compact context projections, fewer autonomous agent
iterations, tighter retry policy, and per-LLM-call telemetry.

## Incident timeline

The supplied application log showed:

| Visible OpenAI HTTP requests | 1 |

The terminal failure was:

```text
DiscoveryResult.capability_classification
The RAG capability must be included when rag_required is true.
```

This inconsistency is now repaired deterministically during model
pre-validation, before OpenAI/Pydantic structured-response parsing completes.
That prevents this specific capability-signal mismatch from aborting
Discovery.

## Current execution shape

The normal first-pass flow can execute:

1. Discovery
2. Product Definition
3. Requirements
4. Market and GTM, when selected
5. Solution Architecture
6. AI Architecture, when selected
7. Security Architecture, when selected
8. QA and Evaluation, when selected
9. Lead Review
10. Targeted specialist revisions, when requested
11. Lead Review again after revisions

Product Planning and Technical Planning use `Process.sequential`, so their task
latencies accumulate. The technical dependency chain is intentionally:

```text
Solution → AI → Security → QA
```

This means the primary optimization opportunity is reducing the size and
duration of each step, not blindly parallelizing steps whose inputs genuinely
depend on earlier outputs.

## Alignment with official CrewAI guidance

### Crews versus Flows

CrewAI describes Crews as suitable for autonomous, collaborative, and
open-ended work. It recommends Flows for deterministic decision workflows,
auditable routing, and precise orchestration.

BuildWise correctly uses a Flow for overall routing. However, most current
Crews contain predefined, tool-less agents that cannot delegate and must
return one exact Pydantic object. A one-agent, one-task Crew provides little
collaboration value for Discovery or Lead Review and still uses the autonomous
agent execution runtime.

Official references:

- [CrewAI introduction and Crews versus Flows guidance](https://docs.crewai.com/core-concepts/Agents)
- [CrewAI Agents](https://docs.crewai.com/en/concepts/agents)
- [CrewAI Flows](https://docs.crewai.com/en/concepts/flows)

### Sequential tasks and context

CrewAI documents that sequential processes execute tasks one after another.
It also relays preceding task output into later tasks and supports explicit
task context.

BuildWise intentionally passes structured outputs down the dependency chain.
As artifacts grow, later prompts become progressively larger. The Lead Review
task explicitly serializes almost every completed artifact into one prompt,
making it a likely latency and context-size hotspot.

Official references:

- [CrewAI Crews and execution processes](https://docs.crewai.com/en/concepts/crews)
- [CrewAI Tasks and task context](https://docs.crewai.com/en/concepts/tasks)

### Context-window handling

BuildWise agents currently use `respect_context_window=True`. CrewAI documents
that this setting can automatically summarize accumulated context when it
becomes too large.

This prevents some context-window failures, but summarization is additional
model work and can lose exact identifiers or references. It should be treated
as a safety mechanism, not a latency optimization. CrewAI recommends
minimizing context accumulation, breaking large work into smaller pieces, and
using retrieval or curated knowledge rather than continually expanding the
prompt.

Official reference:

- [CrewAI context-window management](https://docs.crewai.com/en/concepts/agents#context-window-management)

### Guardrail retries

BuildWise task guardrails are deterministic, but a guardrail rejection asks
the agent to regenerate the task output. The current default allows two
guardrail retries, meaning an invalid output can lead to as many as three
large generations for one task.

CrewAI explicitly documents that the error is returned to the agent and the
task repeats until validation succeeds or `guardrail_max_retries` is reached.

Official reference:

- [CrewAI task guardrails and retries](https://docs.crewai.com/en/concepts/tasks#task-guardrails)

## Current retry and execution controls

The inspected defaults are:

| Control | Current value | Effect |
|---|---:|---|
| `CREWAI_REASONING_ENABLED` | `false` | Prevents separate reasoning-plan attempts |
| `MAX_AGENT_ITERATIONS` | `4` | Allows up to four agent turns per task |
| `AGENT_TASK_RETRY_LIMIT` | `0` | Disables CrewAI agent execution retries |
| `LLM_MAX_RETRIES` | `2` | Allows provider/network retries |
| `MAX_RETRIES_PER_OPERATION` | `2` | Allows task guardrail regeneration |
| `LLM_REQUEST_TIMEOUT_SECONDS` | `240` | Permits one provider call to run for four minutes |
| `MAX_EXECUTION_SECONDS` | `900` | Permits one agent task to run for fifteen minutes |

Disabling CrewAI reasoning removed one important multiplier. Setting agent
execution retries to zero also prevents CrewAI from repeating a failed task at
that layer. Provider retries and guardrail retries can still multiply work
under their respective failure conditions.

The inspected incident contained only one provider request, so retries did not
cause its normal-call latency. The request was intrinsically slow because of
the structured generation size.

## Root-cause ranking

| Priority | Finding | Confidence | Impact |
|---:|---|---|---|
| 1 | Large structured response schemas and large generated artifacts | High | Very high |
| 2 | Full upstream artifact JSON accumulates in sequential downstream prompts | High | Very high in later stages |
| 3 | Tool-less deterministic tasks run through autonomous Agent/Crew execution | High | Medium to high |
| 4 | Guardrail failures can regenerate an entire large artifact twice | High | Very high when triggered |
| 5 | Lead Review receives nearly the complete consultation state | High | Very high |
| 6 | Up to four agent iterations remain available | Medium | High if the agent does not finalize immediately |
| 7 | Automatic context summarization may add calls on large later prompts | Medium | High when triggered |
| 8 | Frontend polling produces noisy logs | High | Low processing impact |
| 9 | CrewAI tracing upload | Medium | Low relative to model generation |

## Recommended target design

```text
BuildWise Flow
  ├─ compact structured LLM extraction
  ├─ deterministic normalization and enrichment
  ├─ compact specialist generation
  ├─ deterministic cross-reference validation
  ├─ targeted Crew only for open-ended/tool-using work
  └─ deterministic blueprint assembly
```

### 1. Introduce compact generation contracts

Start with a smaller `DiscoveryDraft` that contains only semantic decisions:

- interpretations;
- known facts;
- assumptions;
- unknowns;
- risks;
- capability signals;
- clarification questions;
- confidence and rationale.

The application should add or derive:

- artifact and ownership IDs;
- timestamps;
- percentages;
- routing booleans;
- capability-list reconciliation;
- normalized source references;
- the recommended deterministic route.

This reduces schema size and avoids paying the model to produce operational
metadata and cross-field values the application can compute reliably.

Apply the same approach to other large artifacts: model-generated semantic
content should be separated from deterministic IDs, references, totals,
timestamps, derived flags, and formatting.

### 2. Use one iteration for tool-less structured agents

Most agents have no tools, no delegation, and one structured-output task.
These agents should normally use:

```text
max_iter = 1
```

Agents with approved action tools, such as market research, can retain a small
bounded iteration budget such as three or four.

This should be applied per agent based on its action capabilities rather than
by setting one global value that also constrains research agents.

### 3. Tighten retry policy

Recommended MVP defaults:

```env
LLM_MAX_RETRIES=1
MAX_RETRIES_PER_OPERATION=1
AGENT_TASK_RETRY_LIMIT=0
```

Where an inconsistency can be repaired deterministically, the application
should repair it locally instead of regenerating the complete artifact.

### 4. Pass task-specific context projections

Do not send every upstream field to every downstream specialist.

For example, Security Architecture needs a focused projection containing:

- components and trust boundaries;
- data classifications;
- identities and access paths;
- integrations;
- AI data flows;
- deployment assumptions;
- compliance and sensitive-data signals.

It generally does not need the complete roadmap, every market segment, all
success metrics, or unrelated narrative.

The Flow should construct typed, compact input projections for each
specialist.

### 5. Replace the full-state Lead Review prompt

Build a deterministic review index containing:

- artifact decisions and confidence;
- required/selected artifact presence;
- unresolved limitations;
- cross-reference validation results;
- cost totals;
- security and compliance flags;
- traceability coverage;
- deterministic validator findings.

The Lead Reviewer should inspect this compact index and only the small
artifact sections relevant to unresolved findings. It should not receive the
complete consultation state by default.

### 6. Add per-LLM-call telemetry

Crew-level duration is insufficient because it does not explain which
provider call, retry, conversion, summarization, or task consumed the time.

Record:

- consultation, Flow, Crew, task, agent, and trace IDs;
- model and provider;
- request start, first response, completion, and failure times;
- input, cached-input, output, and reasoning tokens when available;
- prompt/context character or token estimate;
- strict response-schema size;
- agent iteration number;
- provider retry number;
- guardrail attempt number;
- context summarization events;
- output-validation duration and error category.

CrewAI exposes callbacks, event listeners, tracing, and usage metrics that can
feed this application-level telemetry.

Official reference:

- [CrewAI Crew usage metrics](https://docs.crewai.com/en/concepts/crews#crew-usage-metrics)

## Recommended implementation order

| Order | Change | Expected result |
|---:|---|---|
| 1 | Add per-call telemetry and context/schema measurements | Establish trustworthy latency evidence |
| 2 | Set tool-less structured agents to one iteration | Prevent unnecessary autonomous turns |
| 3 | Reduce provider and guardrail retry defaults to one | Bound failure cost and latency |
| 4 | Introduce compact `DiscoveryDraft` and deterministic assembly | Reduce first-step latency and failure rate |
| 5 | Add typed specialist context projections | Prevent downstream context growth |
| 6 | Replace full-state Lead Review input with a review index | Remove the largest likely prompt |
| 7 | Apply compact draft/assembly contracts to remaining artifacts | Reduce latency throughout the Flow |
| 8 | Re-measure p50, p95, tokens, failure rate, and revision quality | Validate improvements without degrading blueprint quality |

## Success criteria

The redesign should be evaluated using:

- p50 and p95 latency per LLM call, task, Crew, and Flow stage;
- input and output tokens per artifact;
- schema and context size per call;
- number of provider requests per task;
- number of guardrail regenerations;
- number of context summarizations;
- structured-output failure rate;
- consultation completion rate;
- estimated LLM cost per completed blueprint;
- blueprint validation and Lead Review approval rates.

Latency improvements must not be accepted if they materially reduce artifact
completeness, traceability, architecture consistency, security coverage, or
blueprint usefulness.

## Conclusion

The current runtime is not stuck in an infinite loop. It is asking models to
generate very large, deeply validated artifacts through sequential CrewAI
tasks. One slow structured request can consume more than two minutes, and a
validation or guardrail failure can discard that work.

The correct response is to reduce what each model must read and produce,
derive operational fields deterministically, reserve autonomous Crew behavior
for tasks that actually need it, and measure every provider call separately.
Longer timeouts alone will only make slow failures take longer.
